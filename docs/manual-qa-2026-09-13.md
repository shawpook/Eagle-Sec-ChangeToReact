## 修复记录

### F1（Q1）：Context 菜单项补 `.context-menu-item-wrap` 包装层

- **根因**：`src/app/css/app.css` 中 65 条 context-menu 规则全部以
  `.context-menu .context-menu-items .context-menu-item-wrap .context-menu-item` 三级选择器书写
  （原版 Angular ng-repeat 每项外包一层 wrap）。React 移植 `components/stage7/ContextMenu.tsx`
  的 `renderItem` 把 `.context-menu-item` 直接渲染在 `.context-menu-items` 下 → 样式全失配
  （块级堆叠、行高塌陷、快捷键换行叠字）。同仓库 `collect-window/contextMenu.tsx` 移植正确可作对照。
- **改动**：sortable / plain 两分支的 `menu.items.map` 外各包一层
  `<div className="context-menu-item-wrap" key>`；确认 app.css 无 `>` 直接子元素选择器依赖后最小改动。
- **验证**：HMR 后实机重开「+」菜单 → 行高/图标/右对齐快捷键/子菜单箭头全部正常（截图确认）。
  影响面：全部 ContextMenu.open 弹出菜单（+菜单、右键菜单、排序面板、筛选 pin 菜单等）。

### F0（记录）：启动日志 `Service plugin load failed: H:\dev\plugins\example-service-plugin`

### F2（Q2）：SubmenuPane 定位改回 offsetParent 相对

- **根因**：原版（bundle 16350-16393）`top`/`left` 取 jQuery `position()`（offsetParent 相对），
  `offset()`（页面相对）只用于视口边界检查。React 移植时 `left` 写成 `offset.left` →
  子菜单 left = 菜单left + 项left + 项宽，双重偏移。
- **改动**：`const left = Math.max(-offset.left + 20, position.left + outerWidthOf($menuItem) - offsetX - 4)`。
- **验证**：实机悬停「自动导入」→「设置」子窗格紧贴父项右侧（截图确认）。

### F3（Q3）：移植文件夹导入链到 `services/uploadService.ts`

- **根因**：`uploadFolderToSidebar`（及其依赖 `getFolderList`/`walkTreeSync`/`treeDepth`/
  `createFolderStruture`/`uploadFilesFromFolder`，bundle 53152/8097/8137/8186/8109）未随 React
  迁移；`importFolders` 与空库 ListRegion 导入按钮调用即抛 ReferenceError（promise 静默）。
- **改动**：五函数逐字移植，scope 面 → React 等价：
  `$scope.folders.push` → `useFolderState().folders.push`（原位 mutation，同 `newFolder` 既有模式）；
  `updateSidebarList`→`machineryUpdateSidebarList`；`openFolder`→`folderCoreService.openFolder`；
  `saveFolderDebounce`→`machinerySaveFolderDebounce`；`calculateImageBinding`→`machineryCalculateImageBinding`；
  `changeSidebarIndex`→`machineryChangeSidebarIndex`；`uploadFiles`/`showUploadQueue`→本模块/`machineryShowUploadQueue`；
  `eagle.utils.tree.walk` → 本地等价 `eagleTreeWalk`。深度/数量护栏 swal 对话框与 i18n 插值原样保留。
- **验证**：实机两批导入（27 文件 + 8 文件）：侧栏出现对应文件夹并计数（27/8）、全部 202→229→237、
  后端 `itemCount` 223→250→258、条目自动选中、缩略图生成、文件夹标签挂到检查器。全程无报错。

### F4（Q5/Q6）：shims 桥接 main 逐文件导入回程 + 去重守卫 store 化

- **根因**：main `item:import-files` 逐文件 `event.sender.send('file-uploaded', item)`，
  但 shims 的 `desktopApi.onIpc` 桥接列表缺该通道 → 渲染层收不到；条目只能等 invoke 整体
  resolve 后由 `emitImportedItems` 批量入列 → 大导入时进度条恒停 0/N、网格长时间无流式反馈。
  另外 shims emit 覆写的 file-uploaded 去重守卫依赖 `window.angular`（已退役，恒 null），
  一旦补桥接就会因守卫失效出现双插。
- **改动**（`frontend/public/shims.js`）：
  1. emit 覆写守卫：angular 缺席时回落 `__eagleScopeRegistry.read('raw')`（与 `useItemState.raw`
     同一数组）→ 桥接 emit 与 emitImportedItems 收尾 emit 天然幂等（第二次 emit 被 raw 已含该 id 拦截）。
  2. onIpc 桥接列表补 `file-uploaded`（先 `mergeCachedItems` 再 emit）、`thumbnail-generated`、
     `rebind-refresh`（后两者为 set-custom-thumbnail 承诺链与刷新面的既有回程语义，
     bundle 时代 background 同型——此前在 Electron 下这些回程事件全部丢失）。
- **验证**：重载后第二批导入：进度条正常走完并关闭、8 项流式插入并自动选中、无双插
  （237 = 229+8 恰好一次）。`set-custom-thumbnail`/`rebind-refresh` 回程恢复（后续实机验证自定义封面）。

### F5（Q7）：BoxList rAF 自纠错重试收敛网格布局

- **根因**：v4（@egjs/infinitegrid 4.13）布局管线依赖 ResizeObserver 异步测量；
  `renderItems()` 在「新 children 提交、测量回调未回」窗口被调用后管线停摆 → 全网格
  条目无 inline 定位（CSS `position:absolute; top:3px; left:16px` 默认值叠加），
  视觉上「只剩 1 个条目」。触发面：冷启动首屏、会话恢复、任意运行中视图切换。
- **改动**（`components/grid/BoxList.tsx`）：渲染 effect 中同步 `renderItems()` 后，
  rAF 循环检查首个 `.box` 是否已被 v4 写入 inline `absolute` 定位；未定位则重调
  `renderItems()`（上限 30 帧，定位成功即停）。每次渲染的 cleanup 取消未完成的 rAF。

## 2026-09-14 第四轮：网格显示/缩放四症根因定位与修复（F23/F23b–e、F24）

用户复测症状：「首页缩略图缩放失常（同缩放下个别图像尺寸差异巨大）／进入详情后拉缩放比例不变／
右侧滚动条与实机滚动速率不匹配／各项目显示比例不完全正确／首页没有显示全部资源」。

**结论：全部落在 v3→v4 引擎迁移的结构性缺口上，与 F15–F15e 无关。** 四项修复各自有量化实测：

### F23 — 布局比例源错了（症状「尺寸差异巨大 / 比例不正确」）
- 根因：v4 `JustifiedGrid` 的 item ratio 来自 **box 的 DOM 实测尺寸**。本应用 `.box` 高度 =
  thumbnail 高 + 文件名/元信息块（实测 49~91px，随文件名换行浮动）→ 测得比例 (boxW/boxH)
  严重偏离真实图片比例（16:9 图实测成 1.13），且每次布局自我反馈漂移。
- 修复：`.thumbnail` 加 `data-grid-maintained-target`（v4 官方出口）。语义 = 以该子元素比例为准、
  其余部分作为 `contentOffset` 逐项扣除 → ratio = boxW/(boxH−标签块) = 缩略图真实比例。
  bundle 时代 v3 布局直接用 `item.width/height` 元数据算比例、不依赖 DOM 实测，本属性是等价出口。
- 实测（`ratioErr` = 前 12 条中缩略图渲染比例与 naturalWidth/Height 偏差 >3% 的条数）：
  h150 / h400 / h600 三档均 **ratioErr = 0**。

### F23b — sizeRange 被 DP 常数项淹没（症状「拉缩放图像比例不变」）
- 根因：v4 `JustifiedGrid._getCost` 在 `stretch`/`isCroppedSize` 都为 false 时，把越界行高代价写成
  `(rowSize−min)² + max²` —— **每行都付一次 `max²` 常数** → 最优化退化成「最少行数」
  = 每行塞满 `columnRange` 上限 8 个 → 行高由「填满容器宽度」倒推（实测 `imageSize.height=710`
  时行高恒 116、8 个/行，与滑条值完全脱钩）。
- 修复：`gridProps` 加 `isCroppedSize: true`。`_setStyle` 会显式 `rowSize = clamp(fitRowSize, min, max)`
  （bundle 时代 v3 `JustifiedLayout` 的 minSize/maxSize 语义）。
- 实测：h150 → 行高 153–160；h400 → 390–410；h600 → 590–610（全部落在目标 ±10 内，跨行一致）。

### F23c — 只有第 0 组被布局（症状「没有显示全部资源」）
- 根因：旧实现把 allData 全量（242 条）当 children，靠 `data-grid-groupkey` 每 60 条切组。
  v4 的无限滚动模型只布局被游标命中的组 → 实测只有第 0 组定位，其余 182 条 `cssRect=(top:-9999)`；
  且第二组被提前测量（缩略图未加载 → ratio 失真）反向污染后续布局。
- 修复：**只把当前页切片交给 v4**（bundle 时代 v3 同样「一组一页」），切页仍由
  `resetNgLayoutData(allData, page)` → `startCursor` 驱动，容器高度 = 当前页高度。
- 实测：任意页面 60/60 条全部定位、0 个 `-9999` 幽灵。

### F23d — settle 自纠错循环被自己的占位样式骗过（切页后整页不布局）
- 根因：rAF settle 的判据是 `style.indexOf('absolute') !== -1`，而 v4 给「已挂载未定位」条目写的
  占位样式 `position:absolute; top:-9999px; left:-9999px;` **同样含 absolute** → 第一帧即自我判定
  「已定位」停止重试。实测拖滚动条到第 3 页：`groups=1000003`、60 个 box、`rect.top=-9950`、
  `containerManager.rect.height=0`，要等下一次无关重渲染才自愈。
- 修复：判据改为「容器内是否仍有 `-9999` 占位条目」，并连续稳定 3 帧才收敛（预算 60 帧）。
- 实测：拖到第 3 页 → `firstRects=[49,49]`、scrollTop=0（页首）。

### F23e — 组 outlines 用错坐标源（症状「滚动条与滚动速率不匹配」）
- 根因：facade 的 `ig._items._data[*].outlines` 用 v4 `GridItem.rect` 现算 —— 那是**测量阶段**的
  原始矩形，与最终布局位置无关（实测第 1 页内容 0~2044，rect 却算出 `start=[3] end=[423]`）。
  `gridDirectives` 用它反推页内小数比例 → 滚动位置与滑块位移彻底对不上。
- 修复：改用 **`cssRect`**（布局后写入 style 的坐标，无则回退 `rect`）。
- 实测：outlines = 0~2300；滑块位移严格跟随（滚满一页位移恰 = 轨道 1/5，与拖拽映射互为逆运算）。

### F24 — 详情缩放滑条从未生效（症状「进入详情后拉缩放比例不变」）
- 根因：原 Angular 侧 `$watch("sliderZoomRatio")` 的 listener（把滑条百分比落到 smoothZoom 引擎）
  **未移植** —— 旧代码只写 scope 字段 + `syncDetailFromScope()`，滑条数值/进度条会动，但
  `detailZoom()` 实例的 `rA` 与图像尺寸恒不变（实测拖到 150/40：`rA` 恒 0.73、img 恒 1076×788）。
- 修复：`DetailToolbar` 的 `#detail-slider-ratio` onChange 补调
  `machineryUpdateZoomRatio(value, undefined, undefined, false)`（与 `machineryZoomActual` 同源路径：
  `imageSize.zoomRatio` → `detailUpdateZoomRatio` → `zoomRatioExp` + `focusTo({zoom,pageX,pageY,speed:0})`，
  锚点不传 = 视口中心），并在其后补一次 `syncDetailFromScope()`（`detailUpdateZoomRatio` 内部
  「先 sync 后 set zoomRatioExp」的顺序在本仓快照式 store 下会让右上角 % 徽标固定滞后一次）。
- 实测：滑条 150 → `rA`=4.5 / img 6633×4860；40 → 0.4 / 590×432；100 → 1.0 / 1474×1080（原生尺寸）。

## 2026-09-14 第五轮：用户复测三项（F23g/F23h/F25）

用户复测：「① 加载时全都挤在一起 ② 文件夹内的排列缩略图显示不正常 ③ 缩略图滚轮下拉到切页时卡住，
需要拖滚动条才能继续（并问：原始 Angular 时期就是分页实现吗？）」。

### F23g — 加载/切换瞬间的「全部挤在一起」
- 现场：v4 从「条目挂载」到「写入定位」之间会把**所有**条目渲染在同一个 initialRect 上
  （实测 reload 后 684ms 采样：60 个 box 的 `style.top`/`left` 全等 → 肉眼即全部叠在同一格）。
- 根因：上一轮 F23d 的 settle 判据只认 `-9999` 占位，**漏检这一态**（它没有 -9999）。
- 修复：判据补「多条目共用同一 rect」；重试预算 60 → 180 帧；并在首次布局就绪前把宿主
  `#box-list` 设为 `visibility:hidden`（就绪即显形，60 帧兜底不永久隐藏）。
- 实测：reload 采样 292/496ms → 0 条目且 `hidden`；684ms → 60 条已堆叠但**仍 hidden**；
  841ms → 17 行/33 列、`visible` ✓ 用户看不到堆叠帧。

### F23h — 文件夹内缩略图布局失真（含「同缩放下尺寸差异巨大」的真正收敛）
- 现场：4 张 1152×2048 竖图的文件夹，box 被撑成 261×160 而缩略图只有 70×124 左对齐。
- 根因链：v4 JustifiedGrid 的行高**只能**由「填满容器宽度」反算，`sizeRange` 本身不钳制行高；
  能钳行高的两个开关（`isCroppedSize` / `stretch`）都会额外把行内**条宽**整体 scale 去填满容器，
  而 `.thumbnail` 是「aspect-ratio + max-height」自适应不裁切 → 宽度被撑大缩略图并不会变大。
  另一个独立缺口：v4 默认 `columnRange=[1,8]`，**竖图行凑不到目标高度** —— 实测目标 150 时
  8 张竖图只能得到 263px，这就是用户上一轮「同缩放下个别图像尺寸差异巨大」的最后一块真因
  （F23 修好比例、F23b 修好缩放响应后仍有此残留）。
- 修复：不拉伸（缩略图恒好铺满格子）+ 用 `columnRange` 把每行条数上限设为
  `⌊(容器宽−间隙)/(目标行高 × 页面最小 ratio)⌋`（1..N），让断行 DP 能选出「行高落在
  sizeRange 内」的条数组合，同时不让 DP 逃到「一堆小图凑一行」。
  另：v4 `InfiniteGridGetterSetter` 的 RENDER_PROPERTY setter 用 `===` 比新旧值，React 每次渲染
  都新建数组/函数 → 必须做身份缓存，否则每次重渲染都会触发一次全量重排（隐性循环）。
- 实测（全部页 60 条）：
  - 目标 150 → 行高 `[150,153,150,154,151,151,141]` **极差 13**，缩略图与 box 宽度差 >1.5px 的条数 **0**
  - 4 张竖图文件夹 → box 261×528、缩略图 **261×463**（宽度完全铺满），整行填满宽度、图片变大 ✓
  - 目标 240 / 400 → 极差较大（145 / 285），这是 justified 在「每行 2~4 条、横竖混排」下的固有
    离散性（可选行高只有 288/192/144… 与 400 等距时会并列），非缺陷；如需强行统一行高只能
    牺牲「填满行宽」，会回到 F23h 的失真态。

### F25 — 滚轮越界自动翻页（回答「原版是分页实现吗」）
- **原版确实是分页数据模型 + 连续滚动**：`ng-grid-layout.js` 用 `eg.InfiniteGrid`
  `{isOverflowScroll:false, threshold:2000}`，滚动接近末尾触发 `requestAppend` 把下一页
  `ig.append(items, groupKey)` 变成新组，容器随之变高 —— 滚轮不需要碰滚动条；右侧自定义
  滚动条（`handleDrag` → `resetNgGridLayoutData(allData,targetPage,decimal)`）只是额外的
  「按页跳转 / 精确定位」手段。
- 现状：v4 迁移后 children 只覆盖当前页（F23c），滚到底就是容器底 → 卡住。
- 修复：保持「一页一容器」模型（保住已修好的行高/比例/懒加载链路），在 `#box-container` 上
  接住滚轮方向：页尾继续向下 → 下一页页首（`scrollPercentage:0`）；页首继续向上 → 上一页页尾
  （`scrollPercentage:1`，视觉接续）。累计 80 delta 才翻页（触控板/惯性防误触），停顿 400ms 重置，
  Ctrl/Alt（缩放）与拖动滚动条期间放行。
- 实测：连续下滚 40 拍 → 页面 1000000 → 1000002 →（继续）1000004；反向 4 拍 → 回到 1000000；
  全程无卡死。`goToPage` 走原版同一条路径，页内小数定位与滑块联动沿用 F23e/F21。

## 2026-09-14 第六轮：取消分页，改为一个连续容器

本轮替换第五轮 F25 的滚轮翻页方案。列表现在始终使用完整结果集的高度，滚轮和原生滚动条只改变视口，不再切换 60 条一页的数据，也不再通过重新加载修正滑块位置。

### 问题证据与处理

| 证据 | 原因 | 本轮处理 |
|---|---|---|
| 300 条隔离库只挂载当前 60 条，容器高 1465px、视口高 752px；连续向下滚动出现 `360 → 713 → 0`，并触发 4 次 reset | 滚轮越界时替换整页，实际滚动范围始终只有一页 | `BoxList` 根据完整结果集计算布局，仅对 DOM 做视口虚拟化 |
| 自定义滑块把鼠标位移换成页号和页内比例，再重建网格 | 滑块坐标与浏览器实际滚动范围不同，换页后重新映射 | 由原生滚动条直接使用完整 `scrollHeight`，删除旧滑块的分页与补偿逻辑 |
| `gridService` 和 `bundleGlobals` 各有一份 ScrollbarSaver，后者会每 20ms 反复写位置 | 只修改其中一份仍可能由另一个启动入口装入旧实现 | 两处共用同一个实现，以条目 ID 和像素偏移保存位置，目标列表提交后只恢复一次 |
| 原 Angular 用 append/prepend 接续列表；Orcabox 用完整高度占位和视口渲染 | 连续滚动需要稳定的内容坐标，不能用单页高度代替总高度 | 采用完整高度占位，针对 Eagle 的 Justified/Grid/Square/List 四种布局计算几何 |

布局尺寸来自图片元数据，文件名和元信息预留固定空间。缩略图加载或挂载窗口变化不会改变总高度；缩放、容器宽度和子文件夹区域变化时保留可见条目的像素位置。选中项定位可直接到达尚未挂载的条目。静默刷新和筛选移除同步到完整结果集，批量移除只更新一次引擎。

缩略图订阅随条目挂载/卸载，图片源变化时清除旧加载状态；取消离屏图片请求不再调用缺失的 `listImageError` 而抛异常。切换目录时清除旧列表也改为同步执行，避免原来的 40ms 定时清理误删已经载入的新列表。

### 提交前复核（2026-09-14）

后续调查发现 `gridService.machineryAutoScroll` 仍发送 `autoscrollChannel`，但清理旧分页导入时漏留了该导入；最新检查因此出现 493 条诊断。提交前已补齐导入，TypeScript 恢复为 492 条，与本轮改造前日志去除行列号后逐条一致。

`continuous-grid-scroll` 新增沿真实 `machineryAutoScroll → AutoScroll 频道 → 离屏选中项定位` 的闭环断言，确认目标进入视口、列表数据和布局不变、总高度不变且不 reload。普通滚轮不触发引擎通知；显式定位会发送一次正常的导航通知，因此定位测试检查列表数据与布局，而非要求通用通知版本不变。

提交前重跑四布局 10,000 条几何测试、完整 600 条隔离库滚动测试和迁移哨兵，均通过。滚动测试包含滚轮、原生滑块双向拖动/停住、四布局、锚点恢复、目录切换、离屏数据更新和新增自动定位，最终无未处理渲染异常。四次可选截图仍因 Electron 22 捕获超时跳过，行为断言独立通过；本次没有重跑整套 React 回归。
